<decisions_honoured>
02-CONTEXT.md locks the approach for both fixes. Do not re-open any of these.

FIX-01:
- The phase line is the sole author of `phases_cleared`; the points handler
  stops authoring it.
- `complete` closes the final phase -- the last boss kill never produces a new
  phase line, so without this every finished run is short by one.
- Points remain tracked. `points_partial` and the reconnect lower-bound logic
  keep reading them; removing points tracking would break the desync inference,
  which is a different mechanism serving a different purpose.
- Suite 3's cross-check is re-derived from the phase-number sequence plus the
  completion, computed independently from the raw log -- not deleted, and not
  restated from the implementation.

FIX-02:
- All three visible values age by the gap: `time_left` down, elapsed up, bonus
  expiry down. Ageing one and not the others produces a window that contradicts
  itself.
- `saved_at` is wall clock and is the correction term.
- A bonus whose timer lapsed during the downtime is dropped, by the same rule
  the addon already applies to one that lapses while running.
- The run stays marked desynced.
</decisions_honoured>

  <action>
    Make `restore()` apply the correction term it already has on disk.

    Compute the wall-clock gap once, at the top of `restore`, from `data.saved_at`
    against `os.time()`. Clamp a negative gap to zero: a stamp from the future is
    clock skew or a hand-edited settings file, and it must never be able to add
    time to the run. When `saved_at` is absent the gap is zero, which preserves
    today's behaviour of not judging such a blob stale. Fold the existing
    staleness rejection into the same computed value rather than reading the
    clock twice.

    Apply the gap to all three visible quantities:

    - Elapsed: seed `run.started` from `now` minus the saved elapsed *plus* the
      gap, so the elapsed counter comes back having advanced by the downtime.
    - Instance clock: subtract the gap from the saved `time_left` before seeding

    - Bonus expiry: subtract the gap from the saved remaining when computing

      negative result means the bonus lapsed while the addon was gone, and
      `State:bonus()` already drops a not-done bonus whose expiry has passed --
      that is the same rule the addon applies to one that lapses while running,
      and reusing it keeps the record in place so a later progress message from
      the server can still revive it.

    `run.desynced` stays unconditionally true. Ageing the clock corrects the
