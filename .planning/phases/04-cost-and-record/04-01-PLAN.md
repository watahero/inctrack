<objective>
Stop paying for a chat line the addon does not care about, and record what that
cost was before and after in the test report itself.

Purpose: `text_in` runs on every chat line the client receives, forever. Today
every one of them is handed to `strip_colors()` (two `gsub`s, two allocations)
and then to `parser.parse`, which trims it (two more) and runs the timestamp
loop (at least one more) before the cheap rejection gets a look at it. Five
allocations per line, on the game thread, during combat, in a crowded zone. The
cheap rejection is in the right shape and in the wrong place.

And the improvement has to be a number anyone can check later, not a claim in a
summary. The baseline has to be taken **here**, at the head of the phase,
against the parser as Phase 3 left it -- a figure recorded before HARD-02/03/04
would be measuring different code.

Output: a reject-path benchmark that prints both figures in the report every
run; an exported cheap gate in `parser.lua` called from the shell before
`strip_colors`; the timestamp loop gated on a leading `[`; a report-once guard
on the last unrated chat output in the addon; and the `ascii()` fix that keeps a
log-driven failure message printable on a cp1252 console.
</objective>

<hard_rules>
1. **No pre-existing suite's check count may fall.** Floor entering this phase,
   measured 2026-08-29: parser **11819 (exact)**, generic **1 (exact)**,
   tightened 1, replay 888, state 105, adaptability 42, disconnect 23, timers
   31, persistence 40, ui 65, addon 143. Counts may rise. `parser` stays exactly
   11819 and `generic` exactly 1 -- those two are what say the gate reached
   nothing real.
2. **The gate may not reject anything the full path accepts.** This is the whole
   risk of PERF-01 and its failure mode is silent: a dropped line looks exactly
   like a quiet stretch of chat. Two things make it safe and both are required:
   (a) every needle is a literal substring that *every* matcher accepting a line
   must also require, enumerated in the plan below and re-derived from
   `parser.lua` before it is written down; (b) the gate declines to judge any
   line carrying a colour-code marker byte (`\30` or `\31`), because it runs on
   the **raw** message and a code sitting inside a needle would otherwise defeat
   it. A coloured line costs exactly what it costs today, never more.
3. **Zero known defects.** `EXPECTED_XFAILS` stays 0, `EXPECTED_DEFECTS` stays
   empty; no `XFAIL`, `NOW PASSING` or `FAILED` line in any run.
4. **Green under `INCTRACK_LUA=luajit21`** as well as the default backend, with
   identical per-suite counts. The benchmark's *rates* will differ between
   backends -- that is expected and is why no rate is ever a threshold.
5. **Purity boundary.** `parser.lua` gains no Ashita dependency. `parser.relevant`
   is pure Lua over a string and requires nothing.
6. **Zero content knowledge.** The gate's needles are message *shapes* --
   `Incursion [`, `New Objective: `, and so on -- exactly as the shipped cheap
   rejection at `inctrack/parser.lua:366-376` already is. No instance, boss, mob,
   objective or difficulty name may enter it.
7. **`parser.relevant` does not type-guard its argument.** The shell's `pcall`
   boundary has caught a non-string message since 1.0.0, and the addon suite
   forces it with a Lua table (`test/run_tests.py:3277-3300`): the handler's
   first real act must still be a string method call that raises for a table. A
   type guard in `relevant` would turn that into a silent early return and the
   `parse error` check would go red for the wrong reason. `parser.parse` keeps
   its own `type(line) ~= 'string'` guard, unchanged.
8. **Do not undo prior phases' fixes.** Phase 2's CR-01 (`imgui.Begin(name, nil,
   flags)` and the strictly-positional stub), Phase 2's schema `version = 2` and
   the version-1 migration, Phase 3's `render_ok` / `render_off` latches, the
   validator's `is_string` rule, and all three parser tightenings stay exactly
   as they are. In particular the boon glyph group stays `%([^)]*%)` -- it may be
   empty -- and `full_string` does not exist.
9. **Scope fence.** PERF-02, PERF-03 and the per-frame options table are plan
   04-02. DOC-01/02 are plan 04-03. PROC-01..04 are v2. IN-05 (NaN/±inf in
   `opt_number`) is deferred and, if ever picked up, wants **re-deciding** rather
   than applying as written. Note, do not fix.
10. **No rate is ever an acceptance threshold.** Wall-clock figures are
    machine-specific and are printed as notes. The *checks* are the deterministic
    counters -- `strip_colors` calls and `gsub` calls over a fixed corpus -- plus
    a single same-run, same-corpus comparison of the two shapes.
11. **The gsub counter is opt-in and is never installed on a timed host.** It is
    a Lua wrapper and it costs time; a host that is being timed must run the
    unwrapped `string.gsub`. The counting pass and the timing pass are separate
    passes on separate hosts.
12. `grep -c` exits non-zero when it counts zero. Any acceptance command whose
    passing answer is `0` carries a trailing `|| true` and is judged on the
    printed number, never the exit status.
</hard_rules>

  <behavior>
    Written before the implementation; each is an assertion by the end of this
    task.

    - **A colour-free line that is none of the addon's business costs nothing.**
      Fired through `text_in`: zero `strip_colors` calls, zero `gsub` calls, no
      run, no chat line, and the message untouched.
    - **A line that is the addon's business still costs what it must.** The same
      counters move, and the run exists -- so the check above cannot be satisfied
      by a gate that rejects everything.
    - **A line carrying a colour-code marker byte falls through.** Two cases: an
      irrelevant coloured line, which pays `strip_colors` and is then rejected by
      the existing anchored gate with no run and no chat; and an Incursion line
      with a marker byte sitting *inside* a needle, which starts a run. The
      second is the safety pin for the whole design.
    - **The timestamp loop does not run unless the trimmed line starts with `[`.**
      The same relevant line with and without a `[HH:MM:SS] ` prefix produces the
      same event, and the stamped one costs strictly more `gsub` calls than the
      unstamped one.
    - **The gate is a superset.** For one example line of every specific and
      every generic matcher, and for every invented-future-content line the
      adaptability suite already drives, the gate says yes. Stated as an
      implication over the fixtures, not as a hand-copied list of booleans.
    - **The gate says no to ordinary chat.** A table of combat, party, linkshell
      and system lines, each of which `parse` already returns nil for.
    - **`parse` behaves identically to before for every line in the corpus.**
      The parser suite's 11819 and the generic suite's 1 are unmoved on 127 logs.
    - **A non-string message still raises inside the handler's `pcall`** and
      still produces exactly one `parse error` line.
  </behavior>

  <action>
    **A. `parser.relevant(line)` in `inctrack/parser.lua`.** A new exported
    function, above `parse`, answering one question: could this line possibly be
    ours? It allocates nothing -- `string.find` with `plain = true` returns
    indices, never a new string -- and it never trims, never strips a stamp and
    never touches a pattern that captures.

    Two rules, in this order:

    1. If the line carries a colour-code marker byte, answer **yes** without
       looking further. This function runs on the **raw** message, before
       `strip_colors`, and Ashita's colour codes are a marker byte plus one
       payload byte that can land anywhere -- including between two characters of
       one of the needles below. A line with a code in it is a line this function
       is not entitled to judge, so it declines to. That line then costs exactly
       what it costs today and no more.
    2. Otherwise, answer yes when the line contains any one of the literal
       substrings every matcher requires. Re-derive that list from the matchers
       yourself before writing it down; the derivation is the safety argument and
       it is a paragraph in the SUMMARY. It comes out as the Incursion tag, the
       two objective prefixes, the boss-hint prefix, the tail of the
       remaining-minutes line, the tail of the points line, and the phrase that
       introduces a boon -- seven searches, each `plain`, each a substring that
       the corresponding matcher's own pattern cannot match without.

    Note in the comment that this is deliberately looser than the anchored
    rejection inside `parse`, and why: this one runs on unnormalised text and may
    only ever produce false *positives*, which cost one wasted `strip_colors`,
    while a false negative loses a line the server did send and looks exactly
    like silence. The anchored rejection stays where it is and keeps doing the
    precise half of the job.

    Do not give this function a type guard. Hard rule 7 says why.

    **B. `parse` calls it first.** After the existing `type(line) ~= 'string'`
    guard and before `trim`, ask the same question of the raw line and return nil
    when the answer is no. Then trim; then run the timestamp loop **only** when
    the trimmed string's first byte is `[`; then the empty check; then the
    shipped anchored rejection, unchanged; then the matchers, unchanged. Two
    gates, and both stay: the pre-gate saves the allocation, the anchored gate
    keeps the precision, and keeping both means the only new risk in this change
    is a pre-gate false negative, which rule A is built to make impossible.

    **C. The shell asks before it allocates.** In `text_in`, between the
    nil/empty check and `strip_colors`, return early when the gate says no. That
    is the only place the cost can actually be avoided -- `strip_colors` is the
    shell's call, not the parser's, and no reordering inside `parser.lua` can
    reach it. Say that in a one-line comment.

    **D. The checks.** Extend the existing "costs nothing" block in the addon
    suite with the counter assertions and the two coloured cases, using the
    opt-in `gsub` counter from Task 1. Put the superset and rejection tables in
    the adaptability suite, which runs without chatlogs and is already the suite
    about the parser surviving content it has not seen. Write the superset check
    as an implication over the fixture lines rather than a copied list of
    expected booleans, so a matcher added later is covered by adding one fixture.

    Failure messages say what the player would lose -- a line the server sent
    that never reached the window -- not which predicate returned false.

    **E. Turn on the benchmark's checks.** Task 1's benchmark now has two
    different shapes to compare. Add: `strip_colors` calls over the colour-free
    part of the corpus are zero for the new shape and one per line for the old;
    `gsub` calls over the colour-free part are zero for the new shape and
    non-zero for the old; and the new shape's rate is strictly higher than the
    old shape's, measured in the same run on the same corpus. That last one is
    the only wall-clock assertion in the suite and it is safe because the gap is
    a constant factor -- five allocations against none -- not a percentage. Record
    the observed ratio in the SUMMARY.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server chat -> `text_in` | untrusted text, arbitrary bytes, arbitrary length, on the game thread, on every line the client receives |
| server chat -> the cheap gate | the gate now runs on the **raw**, un-normalised message, before colour codes are removed -- a boundary that did not exist before this plan |
| harness -> console | failure text carrying raw log bytes, printed to a console of unknown encoding |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Denial of Service | `parser.relevant` on unbounded server text | low | mitigate | plain `find` only, no captures, no backtracking pattern, no allocation; the number of searches is fixed at seven and independent of the input |
| T-04-02 | Tampering | a gate that silently drops a line the server did send | high | mitigate | every needle is a literal the corresponding matcher's own pattern cannot match without, re-derived from `parser.lua` before it is written; any line carrying a colour-code marker byte falls through unjudged; the anchored rejection inside `parse` is kept underneath; `parser` stays exactly 11819 and `generic` exactly 1 over 127 logs on both backends |
| T-04-03 | Denial of Service | the unrated `parse error:` chat line | medium | mitigate | report-once latch in the shape 03-01 established, cleared by `/incursion reset` and by a character change |
| T-04-04 | Information Disclosure | `tostring(err)` on a foreign error value reaching a format string | low | mitigate | the error text stays an argument and never becomes the format string; already true and pinned by the existing check that a `%` in server text does not reach `printf`'s first slot |
| T-04-05 | Denial of Service | the harness's own report dying on a cp1252 console | medium | mitigate | log-derived text goes through `ascii()` via one shared helper, and the helper is unit-tested by encoding its output as cp1252 in a suite that runs on every machine |
| T-04-06 | Spoofing | a benchmark figure that measures something other than the shipped path | medium | mitigate | the new shape drives the addon's own registered handler; the old shape is a copy taken at a named commit; every corpus line is asserted to return nil from the shipped parser; counters and stopwatch never share a host; no rate is ever a threshold |

No package-manager install task exists in this phase -- the addon has no
manifest, no lockfile and no dependency directory, and the harness's only
dependency (`lupa`) was installed before this milestone began -- so the Package
Legitimacy Gate does not apply and there is no supply-chain row.
</threat_model>
