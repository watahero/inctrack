## Hard rules for this plan

1. **Do not edit anything under `inctrack/`.** Not one character. If a stub
   cannot reach the code, change the stub.
2. **Do not touch `make_lua()`, `new_state()`, `feed()`, `Result.check`,
   `Result.note`, or any of the eight existing suite functions**, beyond the
   additive `xfail` work in Task 3. The 12,841-check baseline is a floor and the
   cheapest way to hold it is to leave the code that produces it alone.
3. **`test/stubs.py` gets no `__main__` block and no CLI.** `python
   test/run_tests.py` stays the single entry point (D-01).
4. Match the harness's existing style: double-quoted Python strings, plain
   functions, no pytest, no third-party imports beyond `lupa`.

**`make_host()`** — a new bootstrap alongside `make_lua()`, not a replacement.
It builds a **fresh** `lupa.LuaRuntime()` on every call, applies the same
`package.path` and `__clock`/`__clockfn` bootstrap `make_lua()` uses, installs
both stubs from `test/stubs.py`, and returns a host handle. Leave `make_lua()`
and every existing suite untouched: the eight suites share one runtime and the
12,841-check baseline depends on it staying exactly as it is. A fresh runtime
per host also gives each scenario clean module state, which matters because
`ui.lua` keeps `short_cache` and `origin_x` at file scope and `inctrack.lua`
keeps one `incursion` table — so scenarios that need a pristine addon build a
new host rather than juggling `package.loaded`.

Fix this public surface; plans 01-02 and 01-03 are written against it:
`make_host(player=..., profile=...)` returning a handle with `lua`,
`require(name)`, `imgui`, `events`, `fire(event, **fields)` (builds the Lua
event table, calls the handler, returns the table so `e.blocked` is readable
back), `chat`, `settings`, `saves`, `sessions`, `switch_profile(dict)`,
`set_party_name(name)`, `tick(seconds)`, `wall(seconds)`,
`strip_colors_calls`, and `addon` (see below).

**`lua_locals(host, fn)`** — the reflection helper. `ui.lua` and
`inctrack.lua` declare every helper as a file-scope `local`, so nothing but
`ui.render` and the registered handlers is reachable by name — and the addon
may not be edited to export them. Walk upvalues transitively with
`debug.getupvalue`, starting from the given function, following function-valued
upvalues, tracking visited functions so a cycle cannot loop, and return a
name-to-value dict. From `ui.render` this reaches the draw functions and
through them `clock_str`, `right_text`, `wrapped`, `bar`, `urgency`,
`replace_plain`, `shorten`, `STAT_SHORT` and `COLOR`. From the registered
handlers it reaches `incursion`, `visible`, `reset`, `persist`, `printf`,
`now` and `MUST_SAVE`. Expose the shell's union as `host.addon`, resolved
lazily over every registered handler plus the profile-switch callback.

If `debug.getupvalue` turns out to be unavailable in the installed lupa build,
stop and report it rather than working around it — plan 01-02's helper coverage
depends on this and the fallback (driving every helper through `render` and
asserting on the call log) is a different plan, not an improvisation.

**`Result.xfail(cond, msg)`** (D-05) — a third method beside `check` and
`note`. It counts toward `checks` like any other assertion, but a false
condition lands in a separate `xfails` list rather than `failures`, and a
condition that unexpectedly holds lands in a third list for "no longer
failing". Docstring it plainly: an xfail asserts the behaviour the addon is
*supposed* to have, and a known defect is why it is false today (D-07).

Update `Result.report()` to match: the fixed-width status column reads `ok`
when clean, `ok (N known defects)` when the suite carries xfails and no real
failures, and the existing `FAILED (n)` form otherwise. Print xfail messages
with a marker distinct from `FAIL`, and print any no-longer-failing entry with
its own marker so a defect fixed early is loud rather than silent. `report()`
keeps returning "no real failures" — xfails must never make the process exit
non-zero (D-05).

Update the module docstring's suite index to name the two suites plans 01-02
and 01-03 add, and add one line explaining what an expected failure means in
this harness and that Phase 2 is where they go green.

Do not add the exactly-three guard here — the third xfail does not exist until
plan 01-03, and a guard that fails for two plans is not a guard.
