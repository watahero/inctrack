# v1.2.0 Milestone Audit — "correctness and cost"

## Summary

This is a milestone that did what it said, at a level of rigour well above the
norm. Every requirement is backed by a test that goes red when the fix is
reverted — I proved fourteen of them myself rather than reading it. The
shipped-code diff contains no scope creep of any kind: identical parser event
kinds, one new internal run-record field, zero new displayed information.

The gaps are real but small and none of them is in the "quietly wrong" class the
milestone existed to close, with one demonstrated exception. They cluster in two
places: **numbers the restore validator lets through**, and **a planning record
that has drifted behind the code it describes**.

Status is `gaps_found`, not `passed`, for nine specific items listed at the end.
Nothing here blocks archiving the milestone; three items want a decision before
the record is frozen.

## 2. Did the milestone honour its own Core Value?

> *What the window shows is either true, or visibly marked as unconfirmed —
> never quietly wrong.*

**Verdict: held in the shipped code, with one demonstrated residual of exactly
the class the question asks about.**

The two named regressions-from-hardening (Phase 2 CR-01, the ImGui call shape no
other addon uses; Phase 3 CR-01, a validator that refused sessions the addon
itself writes) are both genuinely fixed, and both fixes are mutation-pinned in
more than one place. I re-checked Phase 3's CR-01 specifically: `full_string`
returns zero hits across all four Lua files, and the surviving `is_string`
comment argues the reversed position at length. A blank name now draws an empty
row, not a `?` placeholder — less invention, not more.

I went looking for a third of that class. I found one, and it is in a path the
127-log corpus cannot exercise by construction.

### G-1 — the restore validator admits NaN and ±infinity (demonstrated)

`opt_number` tests `type(v) == "number"` and nothing else. `1e999` is
syntactically valid JSON and `tonumber('1e999')` is `inf` on both backends. I
drove the shipped `state.lua` and then the shipped `ui.lua` directly:

```
time_left = +inf   -> restore ok=True
time_left = NaN    -> restore ok=True
kills_max = +inf   -> restore ok=True, kills 3/inf
saved_at  = NaN    -> restore ok=True, time_left AND elapsed both nan
```

Rendered through the ImGui recorder, the header row draws:

```
TextColored '~-9223372036854775808:-9223372036854775808:-9223372036854775808'
```

and `right_text` silently skips its `SetCursorPosX`, so the layout degrades too.

This is not *quietly* wrong — nobody will mistake that string for a clock — so
it does not breach the core value's letter. But HARD-05 promises "a malformed
one is discarded rather than half-applied", and an out-of-range number is
neither discarded nor half-applied: it is fully applied. The validator's own
docstring lists "a kill cap that is a string" as the thing it exists to stop; a
kill cap of infinity walks through.

This is not an unknown. It is `03-REVIEW.md` IN-05, left open with the explicit
note that CR-01's fix "has now decided in the opposite direction, so it wants
re-deciding rather than applying as written." **No re-decision was ever
recorded.** The finding is the one place where the milestone's own review
process flagged an item as needing a decision and then closed without making
one.

Reachability is the project's own standard: the same validator's contiguity
check is justified in comments by "the settings file is one a player can
hand-edit". By that standard this is reachable.

### Other candidates I checked and cleared

- **The v1 → v2 migration.** 1.1.0 *did* write `version = 1` (confirmed at
  `44e0eb1`), so existing players' saved runs migrate rather than being refused.
  Not a silent-loss path.
- **Every field `serialise()` writes is accepted by `valid_session()`.** I walked
  them one by one. `next_boss.name` and each boon name are the only mandatory
  strings, and both writers always produce a string (possibly empty). No
  repeat of Phase 3's CR-01.
- **The colour-marker gate's needle coverage.** Each of the seven needles is a
  literal that the corresponding matcher's pattern cannot match without, under
  every alternation and optional group. I checked all thirteen specific matchers
  and all five generic ones. The `remaining inside this Incursion` needle
  correctly begins after the optional plural. Coverage is sound.
- **`render_off` as a session latch.** Cleared by `/incursion`, `/incursion
  reset` and a character switch; the re-enable path reports what is on screen
  rather than what was asked for. Not a silent disable.
- **`parser.relevant` has no type guard**, deliberately, so a non-string
  `e.message` still raises into the `text_in` `pcall` as it has since 1.0.0.
  Correct: `nil` and `''` are handled above it.

### G-5 — the zero-content-knowledge guarantee is false as written, and one file says the opposite of itself

`ui.lua:17-25` carries eight content names in its layout mockup — a real
instance name, four real mob names, a real NM name, two real boon names — plus a
real difficulty. `parser.lua` carries the same instance name and several mob
names across nine pattern-example comments. `state.lua:678` carries one more.

Directly above the mockup, `ui.lua:12-13` reads:

> `* No instance, boss, mob or objective name appears in this file. Everything`
> `* drawn comes from the run record, which comes from the server's own messages.`

Ten lines later the same comment block names eight of them.

Every phase's verification dodged this identically — "no regression", "nothing
added", "pattern-example comments" — which is true and is not the same thing as
the guarantee holding. It is pre-existing and it is harmless to behaviour: no
code reads any of it, and the addon genuinely survives new server content
without a change.

But two things make it worth naming here rather than waving through. First,
`PROJECT.md` carries it in the **Validated** list — "Zero hardcoded content: no
instance, boss, mob, objective or difficulty name anywhere in the Lua —
existing" — as a settled fact, which it is not. Second, **Phase 4 owned DOC-01,
edited that exact comment block** (appending the nine-row list below the
mockup), and left the self-contradicting sentence standing. `04-VERIFICATION.md`
records it as INFO-02 and correctly declines to call it a Phase-4 regression.
Nobody has yet decided whether to fix the sentence, fix the mockup, or reword
the guarantee to what everyone actually means: *no content name is hardcoded in
any code path.*

## 5. Honesty of the record

**Verdict: the code and the user-facing documents are honest. The
`.planning/` record is not, in five specific places.**

### What is honest, and notably so

- **`CHANGELOG.md` does not overclaim.** `04-VERIFICATION.md` raised WARN-02
  against the sentence "costs nothing"; the final commit (`7e3bf88`, *"correct
  the changelog's cost overclaim"*) rewrote it to "is now turned away before
  anything is built for it: no copy of the line, no colour stripping, no
  pattern run", and then went further and volunteered the coloured-line
  exception in the same bullet. It claims 3.5× where the shipped backend
  actually delivers 4.75×. It claims no in-game verification anywhere. This is
  the correct direction to be wrong in.
- **`docs/design.md` describes the shipped code**, and its two hardest claims
  are machine-enforced by the `record` suite — I broke the suite count and it
  went red. It states the deferred-write durability residual at its real size
  ("the bound is 'the next `d3d_present`', not '16 ms'"), and it states plainly
  that the colour-marker set has zero corpus backing because Ashita's log writer
  strips the bytes on the way to disk.
- **Phase 3's two summaries carry SUPERSEDED notes** and they are good ones —
  they name the finding, state what actually ships, and point at the review.

assert and is not. This is `03-REVIEW.md` IN-04, still open, and the milestone's
own review already said the residual set is larger than the comment enumerates.
Very low probability. Worth one sentence in the comment.

### G-2 — one clause of a ROADMAP criterion has no test

ROADMAP Phase 4 criterion 2 names three things. Two are pinned. The third —
*"the timestamp loop does not run unless the line starts with `[`"* — is not.
I changed `if s:byte(1) == LBRACKET then` to `if true then` in a clone and the
full suite stayed **green**. The mutation is behaviour-neutral (the anchored
gsub finds nothing) and costs one extra `gsub` per *relevant* line; the `cost`
suite only measures the reject path, which returns before `parse()` is reached,
and the `record` suite derives its search count from `parser.relevant`'s body,
not from `parse`'s. One check would close it.

### G-3 — PERF-01/04's headline number depends on a corpus mix nobody can measure

The gate answers an unconditional *yes* to any line carrying a colour-code
marker byte. This is correct and correctness-mandated (a marker can sit inside a
needle), it is honestly documented in `parser.lua`, `docs/design.md` and
`CHANGELOG.md`, and it is `04-VERIFICATION.md`'s WARN-01.

The audit point is narrower: the benchmark corpus is **18 colour-free / 6
coloured**, and the real in-game mix is unknown *and unknowable from the 127
logs*, because Ashita's log writer strips the marker bytes before they reach
disk. FFXI chat is heavily coloured. The deterministic per-class counters
(0.00/0.00 vs 1.00/4.33 colour-free; 1.00/1.00 vs 1.00/4.00 coloured) are honest
and both classes did get cheaper, so PERF-04 is met. The **3.5×** in the
CHANGELOG is a property of that 75/25 mix, not a measurement of what the player
gets. Nothing states this.

### G-4 — HARD-01 is proven against the stub, by design

Worth restating so it is not mistaken for a closed item: `ui.lua` was not edited
at all in Phase 3 (`git diff b2d30cc..HEAD -- inctrack/ui.lua` is 0 bytes) — the
render path was made un-crashable entirely from outside the file that draws,
which is elegant. But whether Ashita's real binding accepts
`pcall(function () imgui.End(); end)` through a metatable `__index` and actually
rebalances a real ImGui stack is unprovable from the harness by construction.
That is in-game item 3.
