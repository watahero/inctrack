<objective>
Get the settings write off the chat thread, stop allocating a table sixty times
a second, and put a bound on the one cache in the addon that can grow for as
long as the client is running.

Purpose: `persist()` serialises the run, encodes it as JSON and calls
`settings.save()` -- and today it does all of that *inside* `text_in`, on the
game thread, on the line that triggered it. Every boon, every objective, every
boss hint, every phase boundary. The frame handler beside it rebuilds a
two-field options table sixty times a second for a function that reads it and
throws it away. And `shorten()`'s memo cache is keyed by server text with no
bound, in a process that stays up for a whole play session.

Output: a dirty mark on the chat thread and a flush from the per-frame handler,
reachable on the unload path too; a hoisted options table; and a memo cache that
drops itself whole at a stated cap and clears when the run does.
</objective>

<decisions_honoured>
`04-CONTEXT.md` locks the approach. Do not re-open any of it.

- **PERF-02 marks dirty on the chat thread and flushes from the existing
  per-frame handler.** The frame handler already exists and already runs every
  frame, so this adds no new timer and no new mechanism. Ashita has no async
  write primitive; inventing one would be a larger change than the problem.
  **A run must not lose data across an unload immediately after a burst -- the
  flush has to be reachable on the unload path too.**
- **PERF-03 caps the memo cache and drops the whole cache when the cap is
  exceeded**, plus clears on run reset. Boon stat strings are few and repeat
  heavily, so LRU eviction is more code for no measurable gain on real traffic.
- **The per-frame options table** allocated sixty times a second in the frame
  handler is in scope, from 03-03's carry-forward list.
- Claude's discretion, exercised and now **fixed for this plan**:
  - The throttle decision stays where it is, in `text_in`. It is arithmetic on
    a number, not a write, and leaving it there means the *policy* the player
    experiences -- immediate for what the server never repeats, five seconds for
    kill counts -- is unchanged and the existing checks keep measuring the same
    thing. Only the write itself moves.
  - The cap is **64**. A run's boons are a handful and their stat strings repeat
    every frame; 64 is far above any run the corpus contains, so the drop can
    only fire on input the server never sent. State the number and the reasoning
    in the comment, not just the number.
  - The cache is cleared **in place**, never replaced with a fresh table, so a
    handle taken by upvalue reflection stays live and the harness measures the
    cache the addon is actually using.
</decisions_honoured>

  <behavior>
    Written before the implementation; each is an assertion by the end of this
    task.

    - **A burst writes nothing on the chat thread.** A run start, an objective, a
      boss hint and a boon delivered back to back through `text_in` leave the
      write count at zero. Not "fewer writes" -- zero.
    - **The next frame writes once.** One `d3d_present` after that burst raises
      the write count by exactly one, and what was written names the instance the
      player is standing in.
    - **A second frame with nothing new writes nothing.** The flag is consumed,
      not sampled.
    - **The policy is unchanged.** A kill count arriving a moment after a
      MUST_SAVE event still does not earn its own write; the same kill count past
      the five-second window does. Measured across frames, so the assertion is
      about the policy and not about when the disk was touched.
    - **The flush runs when the window does not.** With automatic show/hide off
      and no manual override, and again with the window latched off after a
      render error, a burst followed by a frame still writes the run down.
    - **An unload immediately after a burst loses nothing.** No frame between the
      burst and the unload; the settings still come back holding the run, and a
      fresh host loading that profile resumes it with the instance, the phase and
      the boon intact.
    - **A reset does not leave a stale write pending.** After `/incursion reset`,
      a frame does not write a run back over the cleared session.
    - **A character change does not carry a pending write across.** After a
      profile switch, a frame does not write the old character's run into the new
      character's settings.
    - **The frame handler allocates no options table.** The hoisted table exists,
      reads `visible` true, and after `/incursion lock` the flags that actually
      reached `Begin` include `NoMove` -- so the one field that changes per frame
      still reaches the window.

  <action>
    **A. The dirty mark.** Add a field to the `incursion` table beside
    `save_at`, with a comment in the same voice as `render_off`'s: the chat
    thread decides *whether* a write is owed and the frame handler performs it,
    because `settings.save()` is disk I/O and `text_in` runs on the game thread
    on every line the client receives. Say that Ashita exposes no async write, so
    the frame handler -- which already runs, every frame, and already exists -- is
    the mechanism rather than a new timer.

    In `text_in`, the throttle block keeps its decision exactly as written --
    `MUST_SAVE[event.t]` or past the five-second window, and `save_at` still
    updated -- and sets the flag where it used to call `persist()`. Nothing else
    in the handler changes.

    **B. The flush.** At the very top of `d3d_present`, **above both early
    returns**, consume the flag and persist. Consume before persisting, so a
    raise inside `persist()` cannot leave the flag set and retry sixty times a
    second -- the same reasoning 03-01 applied to the render latch. Comment why
    the flush is above the returns: a player with automatic show/hide off, or one
    whose window latched off after a render error, is still playing the run, and
    a flush below either return would mean their run is never written down. Hard
    rule 4 exists because this is the easy mistake.

    The residual, stated rather than hidden: between the chat line and the next
    frame there is a window of roughly one frame in which the run is not on disk.
    A crash inside it loses that one event. That is the trade being made
    knowingly -- against a synchronous disk write on the game thread on every
    line -- and the unload path covers every orderly departure. Write it down in
    the comment; plan 04-03 puts it in the design document.

    **C. The unload path.** It keeps its unconditional `persist()`. Clear the
    flag there too, so nothing is owed afterwards.

    **D. The two clearing sites.** `reset(quiet)` clears the flag alongside
    `render_off` -- it has just cleared the session string itself, so a pending
    write would put a run back over it. The profile-switch callback does its own
    clearing rather than calling `reset()`, so it needs the same line: a write
    owed by the old character must not land in the new character's settings.

    **E. The hoisted options table.** `ui.render` reads two fields and keeps no
    handle on the table -- it is passed, read and dropped -- so rebuilding it
    sixty times a second is pure GC churn, which is the reason `ui.lua` already
    hoists its own `ARG_*` tables at `:68-74`. Declare one file-scope table with
    `visible` fixed true, rewrite only `locked` on each frame, and pass it. The
    `visible` field can be fixed because the handler has already returned above
    when the window is not visible; say so in the comment, because a later reader
    will otherwise wonder.

    **F. The checks.** Rewrite the MUST_SAVE block in the addon suite so each
    site asserts twice: nothing written yet, then written after one frame. Add
    the second-frame case, the not-visible and latched-off cases, the
    unload-without-a-frame case with its resume round trip, the two clearing
    cases, and the hoisted-table cases (reflection for the table, and the flags
    that reached `Begin` for the lock). Failure messages say what the player
    loses -- a run that came back blank after a crash, a window that stopped
    honouring the drag lock -- not which field held what.
  </action>

      number of entries never exceeds the cap on any call. Measured by counting
      the table itself, not by reading a bookkeeping counter, so a counter that
      drifts from the table is caught.

      check above cannot pass vacuously on a cache that simply never filled.
    - **A drop costs memoisation, never correctness.** A string cached before a
      drop still shortens to the same answer afterwards, computed fresh.
    - **The clearing entry point empties it**, and the table handle taken before
      the call is the same table afterwards -- the cache is cleared in place, not
      replaced.
    - **`/incursion reset` empties it.** Through the shell: a run with boons,
      a frame that draws them, then the command, then the cache is empty.
    - **A character change empties it**, by the same route through the
      profile-switch callback.
    - **The window is unchanged.** All six whole-window snapshots still match
      byte for byte, and the existing `shorten` checks pass untouched.
  </behavior>

  <action>
    **A. The bound in `inctrack/ui.lua`.** Give the memo cache a named cap
    constant, an entry counter, and a clearing helper that empties the table in
    place. When an insert would take the cache past the cap, drop the whole cache
    first and start again.

    Comment the three choices, because each is a judgement:

    - *Why a bound at all.* The key is server text and the addon lives as long as
      the client does. Nothing about a stat string is bounded by anything the
      addon controls.
    - *Why the whole cache and not an eviction policy.* Boon stat strings are
      few and repeat every frame, so an LRU is more code for no measurable gain
      on real traffic, and it would be code on the render path.
    - *Why 64.* Far above any run the 127-log corpus contains, so the drop can
      only fire on input the server never sent. A bound that is reached in
      ordinary play would be trading a real cost for a hypothetical one.

    And clear **in place** rather than replacing the table, so a handle taken by
    upvalue reflection stays live -- the harness reaches this cache the only way
    it can, and a replaced table would leave it measuring an orphan.

    **B. The clearing entry point.** Export one function from the `ui` table
    that empties the cache, documented as what the shell calls when the run it
    was caching for is gone. This is the second thing `ui.lua` has ever exported;
    say in its comment why it cannot be inferred from inside `render` instead --
    after a reset there is no run, so the shell stops calling `render` at all and
    the draw function never gets a frame in which to notice.

    **C. The two callers.** `reset(quiet)` and the profile-switch callback in the
    shell. Both already clear run state; the cache clears where everything else
    does. Nothing else calls it -- a new run does not, because a bounded
    display-only cache costs nothing across runs and `begin` is not one of the
    two states the criterion names.

    **D. The checks.** Put the cap, drop, correctness-after-drop and
    clear-in-place cases in the ui suite next to the existing `shorten` checks,
    reaching `shorten` and the cache by upvalue reflection as that suite already
    does. Count the table with a small Lua helper over `pairs`, so what is
    asserted is the cache and not the bookkeeping. Put the `/incursion reset` and
    profile-switch cases in the addon suite, driven through the real command and
    the real callback, with a frame drawn first so there is something in the
    cache to lose.

    Failure messages say what it costs -- a cache that grows for as long as the
    client is up, or a character's boon text still in memory after they logged
    out -- not which counter held what.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server chat -> `text_in` -> disk | the run record is serialised from untrusted server text and written to the settings file; this plan changes *when* that crossing happens |
| the game thread -> `d3d_present` | the flush now runs inside the frame handler, on the thread every addon in the process shares |
| server text -> the memo cache | cache keys are boon stat strings the server chose, in a process that stays up for a whole play session |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07 | Denial of Service | an unbounded memo cache keyed by server text | medium | mitigate | a stated cap of 64 with the whole cache dropped past it, cleared in place on `/incursion reset` and on a character change; a drop costs memoisation and never correctness, which is pinned |
| T-04-08 | Tampering | a run lost in the window between the chat line and the next frame | medium | accept | stated in the source comment and in the design document; the window is roughly one frame, the unload path writes unconditionally so every orderly departure is covered, and the alternative is a synchronous disk write on the game thread on every chat line |
| T-04-09 | Denial of Service | a flush that never runs because the window is not drawn | high | mitigate | the flush sits above both early returns in `d3d_present`, pinned by the automatic-show/hide-off case and the latched-off case, with a negative control proving the placement is what those checks measure |
| T-04-10 | Denial of Service | a raise inside `persist()` retrying sixty times a second | medium | mitigate | the flag is consumed before the write, so a failed flush is not retried on the next frame -- the same rule 03-01 applied to the render latch |
| T-04-11 | Information Disclosure | one character's run written into another character's settings | medium | mitigate | the profile-switch callback clears the pending write alongside the run and the player name, pinned by a check that a frame after a switch does not write the old run |
| T-04-12 | Denial of Service | per-frame allocation in `d3d_present` | low | mitigate | one hoisted table rewritten in place, in the shape `ui.lua` already uses for its own per-frame arguments; the lock path is pinned through the flags that actually reached `Begin` |
